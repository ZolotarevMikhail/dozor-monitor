# Дозор — робот-проверяльщик сайтов

Дозор присматривает за сайтами: проверяет их по расписанию, при падении
сразу сообщает. (Смотрящий за роботами — отдельный продукт,
«Универсальный сторож».)

Проверяет сайты из `config.json`: HTTP-код, скорость ответа, наличие
заданного слова на странице. Хранит историю в `monitor.db` (SQLite),
при падении/восстановлении сайта шлёт алерт в Telegram
(BOT_TOKEN из .env) и перерисовывает страницу `статусы.html`.

## Как запустить (для не-программиста)

1. Открыть Терминал и перейти в папку проекта:
   ```
   cd /Users/nadezda/claudecode/Freelancer/Дозор
   ```
2. Создать окружение и установить зависимости (нужны лишь для проверки
   стиля; сам робот обходится стандартной библиотекой):
   ```
   python3 -m venv venv
   ./venv/bin/pip install -r requirements.txt
   ```
3. Прогон проверки (проверка → база → алерты в ТГ → страница):
   ```
   ./venv/bin/python monitor.py check
   ```
4. Открыть `статусы.html` двойным кликом — там карточки по каждому
   сайту: статус, код, скорость, последние 12 проверок, время работы
   за сутки.
5. Добавить свой сайт — в `config.json` (пункт `sites`):
   ```json
   { "name": "Мой сайт", "url": "https://мой-адрес.ru", "keyword": "слово" }
   ```
   `keyword` не обязателен.

## Команды

| Команда | Что делает |
|---|---|
| `python monitor.py check` | Полный прогон: проверка + база + алерты + страница |
| `python monitor.py страница` | Только пересобрать статусы.html из базы |
| `python monitor.py история` | Последние 20 записей в терминал |

## Секреты

`BOT_TOKEN` и `ADMIN_CHAT_ID` — в файле `.env` рядом со скриптом

## Поведение алертов

- Сообщение приходит только при СМЕНЕ статуса. Лёжащих сайтов бот не спамит.
- **Анти-дрожь**: «упал» — только после **2 подряд** неудачных проверок,
  «восстановился» — после **2 подряд** удачных. Обычное мигание сети
  алерта не даёт (так защищаются все серьёзные системы мониторинга).
- Первое сообщение — это тест: если пришло, алерты настроены.
- **Тихие часы** (по умолчанию 23:00–08:00, поле «тихие_часы» в
  config.json): ночью уведомления не шлются, а копятся в базе;
  утренний прогон отправит их одной сводкой.
- Недоставленное уведомление не теряется: копится и уходит при первом
  удачном прогоне (любым из каналов).

## Второй канал: e-mail (опционально)

Чтобы письма тоже приходили, добавь в `.env` пять строк:
```
SMTP_HOST=smtp.адрес-почты.ru
SMTP_PORT=465
SMTP_USER=логин@адрес-почты.ru
SMTP_PASS=пароль-для-входа-в-почту
EMAIL_TO=куда-слать@адрес-почты.ru
```
Без этих строк робот шлёт только в Telegram (а с EMAIL_TO — пишет
письма в `письма.txt`, имитация).
Ящик любой с включённым доступом по SMTP. Примеры:
- **iCloud (me.com):** `SMTP_HOST=smtp.mail.me.com`, `SMTP_PORT=587`,
  пароль — «пароль приложения» из настроек Apple ID (обычный пароль
  учётки iCloud не подойдёт).
- **mail.ru / Beget-почта:** порт 465, пароль-приложение из настроек
  почтового сервиса.

## Сторож-режим: слежение за «молчаливыми» роботами (стук)

Отдельная услуга — «Универсальный сторож». Дозор — про сайты; тем не
менее сторож-режим встроен в него технически: он смотрит не только за
сайтами, но и за «молчаливыми»
автоматизациями: чат-ботами, выгрузками, бэкапами, скриптами по
расписанию (cron). Такой объект в `config.json` выглядит так:

```json
{
  "name": "Бот заявок клиента",
  "стук": { "токен": "a1b2c3...", "не_тише_минут": 30 }
}
```

Как это работает:

1. На том же сервере, где Дозор, запущен приёмник:
   `python3 стук-приёмник.py` (порт 8618).
2. Робот клиента после КАЖДОГО успешного прогона стучится:
   `curl -fsS http://<адрес сервера>:8618/ping/<токен> >/dev/null`
   (на практике — строка в его cron сразу после задачи).
3. Если стука нет дольше «не_тише_минут» — Дозор шлёт алерт
   как при падении сайта: «робот молчит N мин».

Токен — случайный секрет (создать: `python3 -c "import uuid; print(uuid.uuid4().hex)"`).
Адрес стука сделан полностью латиницей: curl и большинство клиентов
не умеют посылать русские буквы в адресе. Токен в историю и на страницу
статусов не попадает.

## Встроенные автоматизации надёжности

Мелкие проверенные механизмы, работающие сами собой (рецепты Google SRE,
Grafana, SQLite — по итогам ресёрча слабых мест):

- **Замок прогона** (`прогон.lock`): если прогон ещё не кончился, новый
  запуск крона тихо пропускается — проверки никогда не налагаются.
- **WAL-режим базы**: крон-робот и приёмник стука пишут в одну базу,
  не мешая друг другу (ошибки «database is locked» исключены).
- **Чистка истории раз в сутки**: записи старше 90 дней стираются —
  база не растёт бесконечно.
- **Параллельные проверки**: сайты проверяются пулом из 8 потоков,
  медленный сайт не задерживает остальных.
- **Метка «данные устарели»** на странице статусов: если последняя
  проверка старше 30 минут, страница честно сообщает, что робот,
  возможно, не жив.

## Сведение роботов на сервере

Приёмник запускается как служба (на Ubuntu — systemd), Дозор
продолжает ходить по расписанию cron как раньше. На сервере заказчика
система разворачивается тем же набором файлов: monitor.py,
стук-приёмник.py, config.json, .env.

## Что запланировано (продуктовая версия)

- **Алерт идёт заказчику**: у каждого объекта свой канал уведомлений
  (свой Telegram-бот и/или e-mail заказчика) — сейчас каналы заданы
  одним .env для всего Дозора.
- Установка на сервере заказчика (тот же набор файлов, порт приёмника
  открывается только для стука).
